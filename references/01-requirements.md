# 阶段 0–1：可行性核查与需求分析

阶段 0 的目标是**知道哪些话有证据、哪些没有**；阶段 1 的目标是**把用户的意图变成可验收的条目**。两者都不写代码。

## 阶段 0：可行性核查

### 0.1 先写结论范围声明

文档第一句就限定它不是**什么**：

> 结论范围：文档／源码／本机隔离接口验证，**不是**端到端验收。

没有这句话，读者（包括下一个会话的你）会把局部证据当成整体结论。**被误读的文档比没有文档更危险。**

### 0.2 五级证据

见 `references/evidence.md` §1：实测 / 类型·源码 / 官方文档 / 拟定设计 / 未验证。核查文档的每一条结论都要能归入其中一级，并绑定日期、版本、验证范围。

### 0.3 环境基线

见 `references/evidence.md` §3。要做实测，先把环境钉死，并写清基线**不能**证明什么。

### 0.4 隔离实验

对关键外部依赖，做**隔离**实验（独立目录、独立配置、独立端口、`--pure` 类模式），并记录：

| 字段 | 内容 |
| --- | --- |
| ID | `E01`、`E02`… |
| 操作 | 实际做了什么（可复现的命令） |
| 观察 | 实际观察到什么 |
| 可得结论 | 因此能断言什么（**以及不能断言什么**） |

**隔离实验的结论不得冒充产品测试。** 实验是历史特征证据，产品证据另记——这是"证据不可互相冒充"原则最容易破的地方。

### 0.5 缺口台账

把"未验证"升级为带 ID 的台账（见 `references/evidence.md` §4）：`ID | 缺口 | 需要的证据 | 当前处理`。严重的标为"首要阻断门槛"。

**"当前处理"列写口径限制，不写"待补充"**："不提供跨崩溃 exactly-once 承诺"、"不承诺续航数字"、"不虚报达标"。

### 0.6 工作审视报告

每轮工作收尾写四段（见 `references/evidence.md` §5）：原定目标 / 完成情况（复选框）/ 发现的问题与修正 / 下次重点关注。

### 0.7 阶段 0 的出口

- 每条关键结论都有证据等级与来源。
- 缺口台账已建立，阻断项已标注。
- 环境基线已固定，且写明了它的证明边界。
- **缺证据的功能没有进入需求清单。**

## 阶段 1：需求分析

### 1.1 需求表

一行一条，写**意图与边界**，不写验收标准：

```markdown
| 编号 | 已确认要求 |
| --- | --- |
| R07 | 按住录音、松开结束；单次最多 30 秒，到时硬停 |
| R11 | 追加到已有输入框文字末尾，不覆盖、不自动提交 |
| R18 | 用量范围为绑定会话；不显示账号剩余额度，缺失值显示未知 |
```

四条写法要求：

1. **写行为，不写实现**。"到时硬停"是行为；"用定时器中断"是实现。
2. **把禁止项写进需求**。"不覆盖、不自动提交"是需求的一部分，不是补充说明。
3. **不写数值门槛**。数值门槛进验收门槛（`G`）或决策登记（`Q`）——因为门槛需要批准，而批准是另一条时间线。
4. **一行一条**，可被单独引用。

### 1.2 已确认 vs 拟定必须分节

```
## 2. 已确认需求
（用户明确选择的内容）
> 以下均来自用户明确选择；后文带"（拟定）"的内容属于待审阅的工程方案，
> 不能反向视为用户已经批准。

## 4. 推荐组件边界（拟定）
```

**未批准的内容一律在标题里带"（拟定）"。** 这是最省事也最有效的状态标注方式——不需要为每一条加状态列，章节归属本身就承载了状态。

文档头部再给一次文档级状态：

> 日期：<日期>；版本：<版本>（<阶段后缀>）
> 状态：<已批准的部分>；<仍缺什么>；产品能力仍待验证
> **本文不是已实现的软件说明。本轮没有编写代码、没有安装、没有烧录。**

### 1.3 验收门槛独立编号（G）

需求写意图，门槛写数字。门槛单独成表，且**跨增量**：

```markdown
| 门槛 | 判定标准 |
| --- | --- |
| G1 | <可判定的条件> |
```

门槛表的三条纪律：

- **门槛是跨增量的验收主题**，不要把隐私、异常、集成类门槛拖到最后才写。
- **门槛必须可判定**：含样本量、成功条件、时限。不能写"响应较快"。
- **门槛必须包含分母**："5/15/30 秒各 20 次，每组至少 19 次成功；失败**不剔除**"。

测量口径单列一节写清：样本量、分母不剔除、分组不合并、**P50/P95 不替代硬门槛**、失败场景另行单测。

### 1.4 开决策登记

需求阶段就要开决策登记表（`references/decisions.md`）。做法：把需求里每一个"必须由用户拍板"的点抽出来，逐条编号 `Q01`…

典型必须用户批准的：数据外发范围、准确率目标、时延/可靠性门槛、许可证与发布边界、费用授权、以及任何"用户能感知但技术上任意"的产品选择（手势分工、息屏策略、状态展示完整度）。

**不要替用户批准这些。** 同时也不要反复询问已批准项——在决策登记里维护一份"无须重复确认"的清单。

### 1.5 缺口审查（需求质量门）

需求写完后，做一次**跨文档缺口审查**，输出：

```markdown
| 严重性 | 原文定位 | 问题 | 本轮处理 |
| --- | --- | --- | --- |
| 阻断相关故事 | 主设计 §6，131—153 行 | 只有操作 ID，缺少同 ID 不同正文、取消竞态、查询未知处理 | 补充契约 C01—C06 与 TX/TUI 用例 |
```

严重性分级只反映"阻断什么"，不反映主观重要性。常见的高价值发现：

- **"只有主题，没有可执行用例"**——验收门槛写成了一句话主题（"要保证安全"），而不是 Given/When/Then。
- **"只有名称，没有语义"**——接口列了名字，没定义失败行为。
- **"未批准的数值被当成了基线"**。
- **"上游证据被当成产品证据"**。

### 1.6 待审定事项与停止条件

每个阶段末尾列一份待审清单，每条写：**待定什么 / 为什么不能自己定 / 失败时怎么办**。

"**停止条件**"指的不是项目终止，而是：**什么情况下停止推进、回到上一级重新决策。** 三层都要写：

| 层 | 停止条件示例 |
| --- | --- |
| 方案层 | 若关键门槛失败，**重新提交设计选择，而不是自动降级到曾被否决的方案** |
| 发布层 | 未通过门槛不发布"完整可用版"，**也不偷偷用替代手段绕过** |
| 指标层 | 若未达标，报告各阶段耗时后提出选择，**不擅自降低能力或改口径** |

再加一条授权边界声明：

> **设计批准不等于完成实机验证。** 以下验证只能在获得编码／测试授权后实施；当前只定义判定条件。

### 1.7 阶段 1 的出口

- 每条需求有编号、写行为与禁止项、可被单独引用。
- 已确认与拟定在结构上分开。
- 验收门槛独立编号且可判定、含分母。
- 决策登记已建立，未决项都写明了"卡在谁那里、最迟何时需要"。
- 缺口审查表已产出，阻断项有处理动作。
- 停止条件已写明。

**出口不代表可以编码**——编码要等阶段 2 的 DoR（见 `references/02-planning.md`）。
