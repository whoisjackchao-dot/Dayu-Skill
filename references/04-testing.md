# 阶段 4：测试

测试阶段的产出是**可执行的行为规格**，不是"测试通过报告"。这两者混淆，是项目最容易出现自我欺骗的地方。

## 1. 用例表结构

固定四列，不要增删：

```markdown
| ID | 层级 | G / W | T：可观察断言 |
| --- | --- | --- | --- |
| TUI-01 | T | G 目标会话已绑定；W 追加"修复 API" | T：草稿恰为"修复 API"；附件不变；消息数不变；返回 applied |
```

- `G` = 前提，`W` = 动作，合并在一列。
- `T` 独占一列，且**必须是可观察断言**——能观察到的东西，不是"应该正确"。
- **不是用测试替身自行返回预期值。**

### 1.1 写作要求

- **一行一条可观察行为规格**。不要把多个 `When` 塞进一行。
- **断言多用否定式与多分句**，把"发生了什么"和"没发生什么"都写出来：
  > 无提交；不自动切页；不清空输入框；返回 `target_mismatch`。
- **一行可覆盖多场景**，用"分别测试"展开：
  > `G` home、shell 模式、模态对话框、目标不可见/禁用，**分别测试**。
- **`G` 可省略**，只写 `W`（当前提显而易见时）：`W` 已冻结帧在两种 MTU 下编码与重组。
- **参数化合并时，报告必须逐参数列结果**——不能一条通过遮住未运行的分支。

### 1.2 ID 与层级

- ID = **功能域前缀 + 两位序号**（见 `references/ids.md`）。前缀按功能域划分，序号按该域内顺序。
- **层级（T/C/H/D）写在独立列，不编进 ID**——因为同一用例的证据类型可能变化，而 ID 不能变。
- 层级可叠层：`T+C`、`C+H`、`D+C`。

## 2. 执行规则

| 规则 | 内容 |
| --- | --- |
| 文档性质 | 测试设计**不是**可执行测试文件，**也不是**已通过报告 |
| 未执行的状态 | 只有 `NOT_RUN` 与 `BLOCKED`；**`BLOCKED` ≠ `PASS`** |
| RED 优先 | 仅 T 类先写断言并观察真实失败；**C/H 不伪造 RED** |
| 常量前置 | 语义常量必须在相关故事开工前有批准值与单位 |
| 自动化优先 | T/C 默认自动执行；H 类优先自动驱动与采集；**人工只用于不可可靠自动裁决的环节，并记录原因** |
| 禁止批量勾选 | **不得在设计表里批量勾选 `PASS`** |
| 失败留分母 | 失败保留在验收分母内 |
| 同步 | 用例新增或删除，必须同步追踪矩阵与受影响的交付门槛 |

状态枚举见 `references/evidence.md` §10（`NOT_RUN` / `BLOCKED` / `FAIL` / `PASS` / `NOT_APPLICABLE_APPROVED`）。

## 3. 执行记录

每次执行填齐以下字段（缺项等于这次执行无法复核）：

```
用例ID及参数 · 需求/契约版本 · 测试类型 · 环境/设备/固件/插件哈希 ·
fixture出处 · 命令或人工步骤 · 预期 · 实际结果 · 状态 ·
证据路径 · 执行者 · 时间 · 未决Q项 · 清理确认
```

后两个字段值得单独说：

- **未决 Q 项**：这次执行是否依赖某个仍未批准的决定？若是，状态应为 `BLOCKED`。
- **清理确认**：进程、监听端口、临时文件是否清理；用户的既有环境是否被破坏。

## 4. 追踪矩阵

见 `references/ids.md` §4。表结构：

```markdown
| 需求 | 对应测试ID | 节点 |
| --- | --- | --- |
| R01 | TUI-01, REL-01 | M1, M6 |
```

契约与决策的挂接用"状态 + 断言内联 + 批准注记"三种手法，**不需要额外加列**。

## 5. 变异敏感性：测试是否真的在测

一条测试有没有价值，用一个问题检验：**"把被测的校验/逻辑去掉，这条测试会失败吗？"**

- 不会失败 → 这条测试是装饰品。
- 做法：在设计阶段就写明错误变异示例，例如：

  > `TUI-09` 的错误变异示例：**移除去重后同一请求出现两次文字，必须被捕获。**
  > **移除 route 校验必须使测试失败。**

关键错误路径至少要有一个测试能抓住。

## 6. 自动化裁决者的纪律

当用自动评分器、模型裁判或模糊比对来自动化验收时：

- **评分器自身必须有先失败的黄金测试**——先证明它能识别已知的坏样本，再用它判好样本。
- **不得用 LLM 自评作为唯一裁判。** 可以作辅助，但正确性判定必须有确定性依据或人工复核。
- **归一化不得吞掉实质差异**：标点/空格归一化时不得删除路径分隔符、小数点、负号、版本号中的点或代码标识——**不能因为"标点另计"把 `1.5` 与 `15` 视为相同**。
- **不得把大段替换合并计为"1 处轻微修正"**，从而掩盖整句重写。
- 参考文本 / 期望值**运行前冻结**，**不得看到模型输出后改参考以让它通过**。

## 7. 测试环境隔离

- **所有测试隔离真实项目、真实凭据与真实录音。** 测试载荷是人工 fixture，并在文档中标注。
- 用**专用**配置目录、独立端口、测试会话；并确认真实副作用没发生（例如"没有向外部发出消息"）。
- 外部服务用**本地受控服务**，记录实际请求与调用次数。
- **只在明确授权的门槛访问付费云端**，设定费用上限，**不在每次常规 CI 中无控制调用**。
- 语料：仅使用**专门授权**的测试语料；测试 fixture 的持久化不等于可以保存用户日常数据。

## 8. 环境与构建的隔离

构建/运行环境本身也可能成为风险与性能问题，记录并固化为可执行约束：

- 性能差异要**量化**（"某挂载点下 23 分钟仅完成 338/1078；换路径后约 45 秒完成 1078/1078，约 30 倍差距"），并写成一条**必须遵守的规则**。
- 环境阻塞不要绕过，而是**替换方案 + 留证 + 固化成单一入口脚本**（把版本、路径、环境变量全部封在一个脚本里）。

## 9. 阶段 4 的出口

- 每个需求至少一条用例，每个用例有可观察断言。
- 层级已标注，RED 优先只用于 T 类。
- 执行记录字段齐备（未执行的如实为 `NOT_RUN`/`BLOCKED`）。
- 追踪矩阵与用例集合一致。
- 关键错误路径有变异敏感性说明。
