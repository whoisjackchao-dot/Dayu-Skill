# 阶段 6：交付

## 1. 两种"完成"必须分开

| | 判据 | 允许的说法 |
| --- | --- | --- |
| **文档交付完成** | 资料逐份审查、缺口有记录、规格/追踪/交付标准可读且一致、未知事项已登记 | 可交付待审稿；**不得**称"已批准" |
| **产品完整交付** | 被真实使用并满足已批准需求 | 需真实证据 |

**以下均不算完整交付：** `BLOCKED`、`NOT_RUN`、只在 mock 通过、只有截图、只有源码、构建绿、测试总数好看、缺设备或凭据却全标 `PASS`。

**"设计批准不等于完成实机验证"**，也**不等于**可以刷写设备、调用付费服务或公开发布。

## 2. 完整交付 DoD

四类条件**全部满足**才能宣称"项目完整交付"。

### 2.1 功能与行为

- 每条需求 `R` 至少有一条**通过证据**；完整测试目录中全部必需用例已运行通过。
- 所有已批准的核心行为在**真实组合**上工作（安全边界、限额、取消竞态、隐私、完整状态、各供电模式）。
- "结果不确定"有可用的人工处理流程，**不用自动重发掩盖**。
- 明确写出**不承诺**的保证（如不承诺跨崩溃 exactly-once）。

### 2.2 质量与真实性

- 已批准的质量/时延/可靠性/体验标准通过；**统计含失败分母，未达标不改口径**。
- **无已知的违反需求类缺陷**（误填、未授权外发、越权执行等）。例外需用户明确修改范围并同步所有文档。
- 上游文档、类型定义、模拟器、历史实验与本项目真实证据**各自标注，不互相冒充**。

### 2.3 交付件

按"**别人能不能据此重建、运行、排障、退出**"来列清单：

| 类别 | 内容 |
| --- | --- |
| 源码 | 全部组件源码 + **全部实际测试与 fixture**（不是测试摘要） |
| 锁定 | 精确工具链与依赖锁定；协议版本/schema/黄金向量 |
| 许可 | `LICENSE`、`NOTICE`、第三方组件与版本/许可清单；资源（字体/图像）来源与许可 |
| 产物 | 可运行包/镜像 + **SHA-256**；分区/刷写清单（如适用） |
| 文档 | 安装、配置、日常使用、**问题定位**、退出卸载、升级与**恢复**说明 |
| 证据 | 测试结果、RED/GREEN 记录、真实环境证据、性能数据、验收记录、遗留限制 |

三条容易漏的：

- **不把"应用镜像"当"全量刷写包"**——产物要能真的恢复设备。
- **升级失败要能按文档恢复**——交付说明必须包含回退路径。
- **测试与 fixture 要一起交付**，否则"测试通过"无法被复核。

### 2.4 操作验证

- 用**普通用户**安装运行，无需日常管理员权限。
- **不修改全局安全策略**（防火墙、TLS、代理、驱动）。
- 从交付源码能**按文档构建出功能等价产物**。
- 测试进程/监听/临时文件已清理；**用户的既有环境不被破坏**。
- 用户按交付说明完成**完整流程**（安装 → 配置 → 核心操作 → 状态查看 → 失败处理 → 退出）。

> 若要求**逐字节可复现构建**，需**另行批准**；不要默认宣称已达到。

## 3. manifest 与版本标识

- 交付目录附一份 manifest：文件清单 + 版本/哈希 + 构建参数 + 依赖版本。
- **没有版本控制提交时，用内容哈希标识版本。**
- 验收记录必须引用具体源码与产物哈希——"验收的是哪个版本"不能有歧义。
- **不为满足形式而擅自提交或发布仓库。** 版本标识 ≠ 提交/发布授权。

## 4. 脱敏

交付前逐项检查，**不泄露**：

- 真实凭据、密钥、令牌
- 设备标识（MAC、序列号）
- 真实项目名、路径、会话内容
- 用户音频、转写文本、日志中的正文
- 企业内部信息（网络配置、账号、主机名）

**凭据只存于专用的凭据存储**，不进配置文件、命令行、日志、构建产物、测试 fixture。

## 5. 发布授权

发布（建仓、推送、打 tag、发 Release）是**独立授权项**，不是交付的默认部分：

- 本地完整交付与公开发布是两件事，**DoD 不应默认包含公开发布**。
- 若用户已明确"先本地交付、验收后再决定是否公开"，就**不要提前推送**。
- 获得发布授权后，仍需审查：账号、仓库归属、tag 策略、Release 内容、脱敏、许可证与署名。

## 6. 遗留限制的交付写法

不要写"已知问题：若干"。每条写成可判断的条目：

```markdown
| 限制 | 现象 | 影响范围 | 触发条件 | 规避方式 | 是否阻塞 |
| --- | --- | --- | --- | --- | --- |
```

**不为凑数而弱化描述，也不为免责而夸大影响。**

## 7. 交付清单自检

逐条勾选，任何一项不满足就**不能宣称完整交付**：

- [ ] 每条 `R` 有通过证据
- [ ] 无必需用例处于 `BLOCKED`/`NOT_RUN`（或已被用户明确豁免）
- [ ] 已批准门槛全部有验收记录，分母完整
- [ ] 真实组合与故障注入已验证
- [ ] 全部交付件齐备，含测试与 fixture
- [ ] 产物哈希与验收记录一致
- [ ] 许可与第三方清单完整，资源来源已审查
- [ ] 文档覆盖安装/使用/排障/退出/恢复
- [ ] 普通用户可安装运行，无需改全局策略
- [ ] 脱敏检查通过
- [ ] 遗留限制清单已附，阻塞项已处置
- [ ] 发布授权状态明确（未授权则不发布）

## 8. 交付之后

交付不是终点。维护期同样遵守两条：

- **任何修改都要走同样的流程**：契约变更 → 回归 → 证据 → 版本。
- **已发布的 ID 含义不再改变**；新行为用新编号。
