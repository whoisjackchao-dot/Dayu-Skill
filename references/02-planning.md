# 阶段 2：项目规划

规划的目标不是排期，而是**把工作切成能独立演示的纵向增量，并让每个增量开工前都具备可测条件**。

## 1. 里程碑：纵向可演示增量

**反模式**：按组件推进——"固件全写完 → 主机全写完 → 最后集成"。这种切法在第一次集成前没有任何东西可演示，所有风险都堆到最后。

**正确切法**：每个里程碑是一个**纵向切片**，从用户可见的行为出发，穿透所有涉及层。

节点序列从"基线"到"交付"：

| 节点 | 性质 | 出口形态 |
| --- | --- | --- |
| `M0` | 需求与决策基线 | **不是可用软件**；产出可测试需求、决策记录、测试策略、授权边界 |
| `M1`…`Mn` | 纵向增量 | 每个都能**演示一个用户可见行为** |
| 末尾节点 | 候选版本验证 | 全量自动测试 + 真实环境 E2E + 故障注入 + 性能/耐久报告 |
| 末节点 | 完整交付与验收 | 用户按说明书完成全流程；记录引用源码与产物哈希 |

`M0` 值得单独说明：它是**设计就绪节点**，可能已经满足批准条件却仍不能关闭——因为"方案获批"不等于"工程参数已补齐"。区分这两件事。

## 2. 里程碑卡片

每个节点用同一套字段，缺一项就不算定义完整：

```markdown
### M<N>：<名称>

- **用户价值**：用户因此能做什么（一句话，且必须是用户视角）
- **入口**：依赖哪些前置节点 + 哪些契约/决策必须已冻结/已批准
- **交付**：本节点新增的可运行能力和产物
- **测试策略**：本节点哪些部分先测试（T），哪些走契约（C）/实机（H）
- **适用用例**：<用例 ID 列表，含首尾>
- **演示脚本**：具体演示哪几个场景（含**失败场景**）
- **出口判据**：什么条件下可以关闭本节点
- **明确未交付**：本节点**不含**什么
```

最后一项与第一项同等重要。写法示例：

> **明确未交付**：设备采音与云识别，**不能称语音输入器完成**。

> **不算完成**：只用电脑麦克风，或仅模拟数据包，却宣称硬件适配完成。

> **不算完成**：只有静态假数据屏幕、状态靠字符串猜测、数值显示 0 但口径不明。

**"不算完成"清单是本规范里最实用的一节**：它把"看起来做完了"的常见伪装逐个点名。每个节点都该写两三条。

## 3. Definition of Ready（开工前必须满足）

故事进入开发前，七条全中才开工：

1. **一个可演示的用户结果**，对应 `R` 编号；明确写出**不包含什么**。
2. **正常、边界、失败用例及预期**；T/C/H/D 分类已明确。
3. **所依赖的 `Q` 项已决议**；协议字段/阈值/数据来源已冻结到**足够测试**的程度。
4. **测试夹具、环境、可观察输出与清理方法可用**；需要费用或高风险动作的已获**明确授权**。
5. **入口/出口、副作用所有权、取消/重试/去重和资源限额明确**。
6. **能识别 RED 失败原因**；上游探索与业务测试分开；外部阻塞有记录。
7. **与现有系统的兼容范围明确**；有失败后的停止/恢复方案。

**未知能力先进入限范围 spike**，不在未验证假设上批量编码。

spike 的出口可以是"**不支持**"——但**不算功能交付**。此时返回设计并向用户说明，**不静默降低需求**。

### 3.1 常量的批准前置

> `ASR_TIMEOUT`、`FRAME_DRAIN_TIMEOUT`、`STALE_TIMEOUT` 等符号必须在相关故事开工前**有批准值与单位**；**不以任意数字运行后宣布验收**。

这条推广到任何项目：**所有会被写进代码的语义常量，在开工前必须有批准值。** 否则你会在验收时发现门槛是运行时随手定的。

## 4. 契约冻结

冻结的完整机制见 `references/decisions.md` §5–§8。规划阶段要做的是**决定冻什么、什么时候冻**：

- 建一张**冻结时间表**：`契约 | 最迟冻结 | 文件 | 状态`，以里程碑为轴。
- 对每个契约，先出**清单**（列出待定项 + 关联测试），到冻结时点再出**冻结文档**（给出唯一取值）。
- **只冻结"不冻结就没法开始"的部分**，其余登记最迟冻结时间。
- 两端第一次独立实现前，冻结**最小**互操作契约；**不提前建设通用平台**。

### 4.1 一个实用的冻结判据

对每个待定项问：**"如果现在不定，两端会不会各写一个不兼容的版本？"**

- 会 → 现在冻结。
- 不会（只有一端用、或可以后兼容） → 登记最迟冻结时间，继续推进。

## 5. 节点依赖与反馈

**默认路线是风险优先，不是瀑布。** 明确写出这句话：

> `M0→M1→…→Mn` 是默认风险优先路线，**不是必须等待整个模块完成的瀑布流程**。

- 前一节点期间可以独立研究硬件、准备语料、办理授权——**但任何探索不绕过对应用户授权**。
- 每个节点内部继续拆成"一个行为一轮测试/实现/演示"。
- 每个节点开始时登记**执行负责人和验收人**。单人协作时由实施者提供证据、用户批准范围/体验/发布。
- **未约定人员和日期时不填假姓名或工期。**

### 5.1 每次演示记录

| 字段 | 内容 |
| --- | --- |
| 新增可用行为 | 这次真的能做什么了 |
| 所通过用例 | 用例 ID |
| 尚不可用部分 | 明确列出 |
| 用户反馈 | 原话或要点 |
| 下一条故事 | 下一步 |

**若改变接口**：更新契约与黄金向量，跑受影响回归。**不继续堆积依赖已被否定假设的代码。**

## 6. 需要的外部授权清单

规划阶段就要把"需要用户授权才能做的事"集中列出，避免开工后才发现卡在授权上：

- 会**产生费用**的调用（云 API、付费服务）
- **刷写/变更真实设备**的动作
- **数据外发**（哪些字段出网）
- **发布**（仓库、账号、tag、Release）
- **修改全局/系统级策略**

每条写：动作、为什么需要、影响范围、授权状态。

## 7. 阶段 2 的出口

- 每个里程碑卡片字段齐全，含"明确未交付"与"不算完成"。
- 首个故事的 DoR 七条全部满足。
- 冻结时间表已建立，首个节点所需契约已冻结。
- 需要的外部授权已列明并获得（或明确标为阻塞）。
- 演示记录模板已就位。

到这里才可以进入阶段 3。
