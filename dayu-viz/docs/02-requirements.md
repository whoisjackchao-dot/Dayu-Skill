## 1. 目标与可行性结论

dayu-viz 是 dayu 方法论的一个新 DLC：一个本地只读 Web 看板，指向任意 dayu 项目目录，把该项目的阶段、当前节点、阻塞项、待批准项与交接块实时呈现为一屏。可行性结论见 `03-feasibility.md`：本机 Node v24.16.0 与零依赖路线足够，前提是 D: 盘 exFAT 不支持硬链接原子写这一实测约束。

## 2. 已确认需求

> 以下均来自用户明确选择。后文带"（拟定）"的内容属于待审阅的工程方案，
> **不能反向视为用户已经批准**。

| 编号 | 已确认要求 |
| --- | --- |
| `R01` | 提供本地 Web 看板，单项目深视图；不提供多项目总览 |
| `R02` | 只读：看板永不修改被观察项目的任何文件 |
| `R03` | 实时自动跟随：被观察文档变化后，页面无需手动刷新即可更新 |
| `R04` | 覆盖阶段、当前节点、阻塞项（含解除条件）、待批准项（含最迟时点）、交接块 |
| `R05` | 任何读不到的字段显示为"未提供"，**不得**以 0 或空值冒充 |
| `R06` | 交付形态为 dayu 的 DLC：独立目录、拷贝即安装、不依赖 dayu 本体 |
| `R07` | 每个结论可跳回原文行 |
| `R08` | 后端零运行时 npm 依赖；前端无构建步骤 |
| `R09` | 看板可指向任意 dayu 项目目录运行，不改代码 |

## 3. 验收门槛

> 门槛承载数值与判定标准；需求只写意图。门槛跨增量，**不要把隐私/异常/集成拖到最后**。

| 门槛 | 判定标准 |
| --- | --- |
| `G1` | 对 `D:\DSH\docs` 能正确报出阶段 2、当前节点含 M0/M1、阻塞项 SPIKE-B01 及其解除条件、待批准 Q05/Q06 |
| `G2` | 修改任一被观察文档后 ≤ 2 秒内页面自动更新（样本 10 次，10/10 生效；文件写入失败不计入分母） |
| `G3` | `D:\DSH\docs` 中不存在的字段，接口返回 `unknown` 而非空串或 0（抽查 10 个字段，10/10） |

### 3.1 测量口径

- 样本量：`G2` 每组 10 次；`G3` 抽查 10 个字段
- **分母**：失败/超时/异常**不剔除**；文件写入失败不计入分母（写入失败不是被观察系统的一次有效采样）
- 分组：冷启动 / 稳定态 / 重连 / 主动取消**分别报告**
- P50/P95 为描述统计，**不替代硬门槛**

## 4. 架构候选与推荐（拟定）

| 方案 | 优点 | 约束与结论 |
| --- | --- | --- |
| A：零构建本地应用（推荐） | 无构建步骤，改完刷新即生效；后端零 npm 依赖；跨会话接管成本最低 | **已选**（决策 D5） |
| B：Vite + React + TypeScript | 复杂交互的开发效率与可维护性最好，类型安全 | 未选：多一层构建链与 node_modules，跨会话更脆 |
| C：纯静态单文件报告 | 无需服务，最易分享 | 未选：无实时跟随，无法承载多会话与 agent 协作视图（决策 D1） |

> 排除清单：多项目总览、写回项目文档、远程访问、移动端适配、会话全轨迹解析（见设计文档 §11）。
> 若方案 A 的关键门槛失败，应**重新提交设计选择**，而不是自动退到方案 C。

## 5. 待审定事项与停止条件

- `Q01` 是否授权 `git push`（卡在用户，最迟 `M5` 前）
- `Q02` 图表库最终选型（最迟 `M2` 前）
- `Q03` 是否包含 V7 上下文健康度面板（最迟 `M4` 前）
- `Q04` 本机安装位置：是否同时装到 DSH 与 OpenCode 两个技能目录（最迟 `M5` 前）

**停止条件**（不是项目终止，而是"停止推进、回到上一级重新决策"）：

| 层 | 停止条件 |
| --- | --- |
| 方案层 | 解析层对真实文档的字段降级率过高（>30% 为 `unknown`）→ 重新提交解析策略设计，**不自动改为人工录入** |
| 发布层 | 未通过 `G1`–`G3` 不称"可用"，**不用截图或手工演示替代自动化证据** |
| 指标层 | 未达标 → 报告数据并提出选择，**不擅自改口径或降低门槛** |

> **设计批准不等于完成验证。** M1 的验证只能在后续 Task 完成后实施。
