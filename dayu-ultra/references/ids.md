# ID 体系与追踪

ID 存在的唯一理由是**让"这条需求被验证了吗"这个问题有确定答案**。没有 ID，追踪只能靠文字检索，而文字会改写、会措辞漂移。

## 1. 核心原则：编号是坐标，不是标签

- **一个编号在项目生命周期内只指一件事。** 编号一旦发布，含义不再改变。
- **不同类型的对象用不同前缀**，不要混用同一套数字。
- **编号不进正文讨论，只进表格首列**，这样任何一条陈述都能被引用成 `见 R07`、`见 TX-12`。

> 编号连续性与唯一性是本规范的要求，用于保证引用稳定。源项目的文档以连续闭区间（`R01—R24`）引用编号，但**未写明"不得跳号"的规则**——此处作为工程纪律由本规范补入，非原文搬运。

## 2. 前缀分类

前缀按**读者**与**用途**分组，不要按主题分。下表是可直接套用的骨架：

| 前缀 | 类别 | 一句话用途 | 定义在 |
| --- | --- | --- | --- |
| `R` | 需求 | 用户已确认的要求（写意图与边界，不写验收标准） | 需求文档 |
| `G` | 验收门槛 | 跨增量的验收主题与判定标准 | 需求文档 |
| `Q` | 决策 | 必须由用户拍板的事项 | 决策登记 |
| `C` | 契约 | 跨模块/跨进程/跨设备的语义约束 | 契约补充 |
| `A` | ADR | 一次架构选择及其回退条件 | 契约目录 |
| `M` | 里程碑 | 纵向可演示增量 | 规划文档 |
| `B` | 缺口 | 已知未验证项及其所需证据 | 核查文档 |
| `<域>-` | 用例 | 可执行行为规格 | 测试矩阵 |
| `<域>-API-` | 接口 | 接口地图中的单个接口 | HLD |

**用例前缀按功能域划分**（示例，按项目替换）：`SEC`（安全）、`TX`（事务/竞态）、`E2E`（端到端）、`PERF`（性能）、`REL`（发布/生命周期）、`UI`（界面）、`ST`（状态）。

接口前缀按**承载方式**划分：外部付费服务、本项目自有协议、上游原生接口、进程内 API、平台能力、硬件接口、测试专用接口——各成一组，每组有自己的表头与"是否已冻结"声明。

**运行期标识符与文档编号分开管理。** 代码里的 `operationID`、`sessionID`、`attemptID`、`epoch` 等是运行期身份，不是文档编号，但**同样要有"何时改变"的定义**（见 §5）。

## 3. 编号规则

```
<前缀><两位零填充序号>        例：R07、C03、M1 节点内的 TX-12
<域前缀>-<两位零填充序号>     例：SEC-01、PERF-04
```

- 两位零填充，保证字典序 = 数字序。
- 多段前缀用连字符连接。
- 里程碑用 `M0`—`Mn`；`M0` 固定为"需求与决策基线"，不产出可用软件。
- **例外要一致**：若某组从 `00` 起编，全组保持；不要混用。

## 4. 追踪链路

完整链路是：

```
需求 R → 契约/决策 C/Q → 用例 ID → 里程碑节点 M → 验收证据
```

**这条链路通常跨多份文档，不要试图用一张表装下全部。**

分工：

| 环节 | 载体 | 表结构 |
| --- | --- | --- |
| R → 用例 → M | 测试矩阵的追踪表 | `需求 \| 对应测试ID \| 节点` |
| C/Q → 用例 | 用例的 `层级`/状态/注记内联 | 依赖未批准的 Q 或未冻结的 C → 该用例状态为 `BLOCKED` |
| C → M | 契约目录的冻结时间表 | `契约 \| 最迟冻结 \| 文件 \| 状态` |
| 批准值 → 验收基线 | 冻结文档的已批准项表 + 回写声明 | `项 \| 批准值 \| 影响` |

**契约与用例的挂接用三种手法，不必强加一列：**

1. **状态挂接**：依赖未批准决策或未冻结契约的用例，状态直接是 `BLOCKED`（并写明解除条件）。
2. **断言内联**：断言正文引用约束 ID——"取消竞态按 C03 裁决"、"按 C04 取得终态证明"。
3. **批准注记**：在该用例旁记录"Q08 已于 <日期> 批准，关联 TX-10/TX-11/TX-12"。

**验收基线要有回写声明**：批准值写入契约后，在就绪报告里明确写出"上述取值已写入 <契约文档> 第 N 节，作为验收基线"。这句话是"批准"变成"可验收"的转折点。

## 5. 运行期身份表

任何有多层身份的系统，都要有一张身份表，列：`名称 | 含义 | 改变时机`。

它的作用不是文档美观，而是**防止把不同用途的 ID 混作一个**（这是分布式/异步系统最常见的一类缺陷）：

- 设备身份 vs 本次启动 vs 一段录音 vs 一次请求 vs 一次写入 —— 各自身份，生命周期不同。
- 「一次操作的身份」在**安全重试时必须复用**，在**新操作时必须新建**。
- 某一层代次（generation/epoch）的旋转必须**使旧回调全部失效**。

**明确写出"不能混用"的那一句**：

> 不能把请求 ID、录音 ID 和会话 ID 混作一个 ID。

## 6. 维护规则

- **用例新增或删除，必须同步追踪矩阵和受影响的交付门槛。** 矩阵漂移 = 追踪失效。
- 用例 ID 的**层级**（T/C/H/D）写在独立的"层级"列，**不编进 ID**——因为同一个用例的证据类型可能变，而 ID 不能变。
- 不要给每个段落都编号。**只给需要被引用的东西编号**：需求、决策、契约、用例、里程碑、缺口、接口。散文不需要编号。
- 矩阵中每条需求至少有一个用例；没有用例的需求，说明它还不可验收——回到需求阶段补齐，或明确记为"不做"。

## 7. 追踪自检

每次进入验收前，跑一遍这五个问题：

1. 每条 `R` 是否至少有一个用例，且节点已标注？
2. 每个用例是否至少挂到一条 `R`？（孤立用例通常意味着范围外功能）
3. 是否有非 `PASS` 的必需用例？列出并确认是否阻塞交付。
4. 是否有取值没有关联测试 ID 的冻结契约？（违反"可测试"约束）
5. 是否有 `Q` 项仍为待批准，却已被当成确定值使用？（漂移，按 `references/decisions.md` §9 处理）
