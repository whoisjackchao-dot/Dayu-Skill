# 决策与契约

本文件管两件事：**谁批准了什么**（决策登记），以及**什么时候必须把某个取值钉死**（契约冻结）。这两件事是同一个问题的两面——不能被追溯的决策，等于没有决策。

## 1. 决策登记表

贯穿项目全程的唯一决策台账。列：

| ID | 决策内容 | 当前依据/状态 | 影响节点 |
| --- | --- | --- | --- |
| Q01 | <要决定什么> | <已批准/待批准/未决 + 依据与日期> | <影响哪个 M 节点或故事> |

规则：

- **未批准不当作事实。** 状态栏只允许三种实质状态：已批准（带日期）、待批准（带卡在谁那里）、未决（带最迟何时需要）。
- **每一行都必须能回答"它挡住谁"**。影响节点为空的行，说明这个决策既不紧急也不属于本项目——考虑删掉它。
- 决策内容写**问题**，不写方案。方案进 ADR（§7）。

## 2. 批准记录：必须记录边界

每项批准除了日期和结论，还要记录三件事。**其中第三件最常被省略，也最重要：**

1. **明确选项**：用户从哪几个选项里选了哪个（"选择 A「清理优先」"）。
2. **受影响用例**：这次批准关联哪些用例 ID。
3. **该批准不覆盖什么**——原文里几乎每次批准都带这一句，形式如：

> （用户对 X 回复"接受"，2026-09-15）。关联 PERF-01、M3/M5；**批准的是验收目标，不是性能结果**。其他事项以当前决策表及后续批准记录为准。

> 该批准**不包含**长按具体时长或新增手势。

> 此回复**不批准**其他 Q02 项目或开始编码。

**为什么必须写第三条**：批准是局部授权，不是全局开关。"方案获批"很容易被下一个会话误读为"可以开始编码 / 刷机 / 调付费 API / 公开发布"。把否定边界写在批准旁边，是唯一能防住这种误读的低成本手段。

## 3. 可逆 vs 不可逆：谁有权决定

| 类型 | 例子 | 谁决定 |
| --- | --- | --- |
| **可逆工程细节** | 测试框架、目录结构、命名风格、内部实现语言 | 执行者自行决定，不必上报 |
| **不可逆产品语义** | 数据外发范围、准确率目标、时延门槛、许可证、发布账号、费用授权 | **必须用户批准**，不得代批 |

判断方法：问"这个决定如果事后要改，代价是什么？"代价是重写几行代码 → 自行决定；代价是用户信任、合规风险、已发布产物 → 必须批准。

## 4. 待决项的登记

阈值、参数、字段布局未定时，登记为待决，**不要自己选一个看起来合理的值**。登记格式：

```markdown
| 项 | 说明 | 关联测试 | 状态 |
| --- | --- | --- | --- |
| 尾帧超时上限 | 起点/单位/上限均未定 | BLE-xx | ⏳ |
```

状态符号约定：`✅ 已批准` / `✅ 已冻结` / `⏳ 清单就绪，取值待冻结` / `⏳ 未开始`。

**"未定"是有价值的产出**，它明确指出哪些地方还不能开工。把未定写成已定，损失的是整个项目的可追溯性。

## 5. 契约冻结的三种形态

同一套机制按成熟度分三种载体，按顺序演进：

### 5.1 清单（未冻结时）

列：`# | 冻结项 | 需要产出的值 | 关联测试 | 状态`

清单的作用是**把"还不知道什么"显式化**：每一项都要求写出"需要产出的值"（具体到字段/单位/范围）和"关联测试 ID"。

> 清单就绪，语料与部分取值未冻结。M3 验收前必须逐项填值。

### 5.2 冻结文档（取值已定）

冻结文档在清单基础上给出**唯一确定取值**，并声明解除了哪些开工阻塞。标准骨架：

```markdown
# M<N> <名称>契约冻结

> 状态：**M<N> 开工冻结（工程取值已于 <日期> 获用户批准）**
> 依据：[C0x]、[HLD §x]、[测试矩阵 §x]
> 冻结日期：<日期>
> **本文件解除 <约束ID>「<原文描述>」的开工阻塞。**

## 1. 冻结范围
## 2. <边界表>
## 3. <接口/格式表>
## 4. <状态机与线性化点>
## 5. <容量与期限（已批准值，日期）>
## 6. 明确不做
## 7. 已批准项（日期 用户确认）
## 8. 变更规则
```

### 5.3 冻结时间表（把多个契约挂到里程碑上）

放在契约目录的入口文件里，列：`契约 | 最迟冻结 | 文件 | 状态`

以里程碑为轴，一行一契约；未建文件写"待创建"；未完成带 `⏳`。这张表回答的是项目级的调度问题：**"哪个节点在等哪个冻结"**。

## 6. 冻结文档的四张关键表

**① 冻结范围二分表** —— 明确"现在钉死什么、什么留到以后"：

| 冻结 | 不冻结（各自里程碑前） |
| --- | --- |
| <本节点必须确定的项> | <先不定的项>（M2 前，见 C07） |

右列每一项都要带 **"（某里程碑前，见某约束 ID）"**。没有时点的"以后再说"等于永远不做。

**② 参数冻结表** —— `符号 | 批准值 | 单位 | 说明`；或 `项 | 冻结值 | 依据`。每个值都要有单位；每个值都要有依据（哪条决策、哪份文档）。

**③ 已批准项表** —— `项 | 批准值 | 影响`，标题带批准日期。批准值必须与决策登记表一致——不一致就是漂移，按 §9 处理。

**④ 明确不做 / 不继承** —— 单独成节，列出**明确排除**的能力与**明确不继承**的上游配置：

> 不提供提交/审批/shell/任意文件/清空草稿接口。
> **不继承**：上游的 `sm_bonding=0`、HID、OTA、未指定加密权限的自定义服务。

这一节的价值高于大多数"我们要做什么"的描述：它防止后续会话"顺手"加上一个被明确排除的能力。

## 7. ADR（架构决策记录）

最小字段，不要更多：

| 字段 | 内容 |
| --- | --- |
| 问题 | 要解决什么 |
| 证据 | 支持判断的证据（带等级，见 `evidence.md`） |
| 候选 | 考虑过哪些方案 |
| 选定 / 未选定 | 选了什么、为什么；未选的为什么不用 |
| 用户批准状态 | 已批准（日期）/ 待批准 |
| 关联 | R / 用例 / M 编号 |
| 回退条件 | 什么情况下这个决策要重开 |
| 实际验证状态 | 未验证 / 已实测（带证据） |

**未选方案必须保留在记录里**，并写明切换规则：

> 方案 B 本次未选择；保留比较记录，切换需重新评审，**不自动回退**。
> 若方案 A 的关键门槛失败，应重新提交设计选择，**而不是自动退到方案 C**。

没有这一句，失败时的默认行为就是悄悄降级到最省事的方案——而那个方案当初正是因为不安全/不满足需求才被排除的。

**无关未来能力不提前抽象。** 只为当前已批准的需求建抽象；"以后可能要支持多供应商/集群/OTA"不是现在建模的理由。

## 8. 冻结的硬约束

- **每个冻结文件必须可测试**：每条取值能对应到**至少一个测试 ID**。对应不上测试的取值，说明它还没有被想清楚。
- **待批准值双轨制**：标"待批准"的工程取值，用户确认前可按提案实现且**必须可配置**，但**不得**在验收文档中当作已批准值。
- **变更规则固定四步**：

  > 更新版本 → 同步契约测试与受影响回归 → 记录 ADR → 不保留未发布版本的兼容包袱

  最后一条是刻意的：未发布的版本不背兼容包袱。背了就会让每个取值永远无法收敛。

## 9. 漂移处理

发现决策登记表、冻结文档、验收文档对同一个值说法不一致时：

1. **不要选对实现最省事的那个版本。**
2. 登记冲突（哪个文件说什么、冲突点是什么）。
3. 修订**所有**受影响文档。
4. 记录 ADR（问题、证据、选定值、为什么）。
5. 如果涉及用户已批准的值被改动 → 必须回到用户重新批准，不得由执行者自行仲裁。

## 10. 不确定性必须是一等状态

状态表必须能表达"不知道"。禁止用 0、空字符串或默认值掩盖缺失。三种缺失要分开：

| 状态 | 含义 | 显示 |
| --- | --- | --- |
| `known(value)` | 有可靠来源 | 显示值 |
| `unknown` | 有该字段，但当前无法取得 | 显示"未知" |
| `not_reported` | 提供方根本不提供该字段 | 显示"未提供" |

**禁止把"读不到"渲染成 0**——"0 费用"和"费用未知"是完全不同的断言。

同理，写入类操作要有 `uncertain` 终态（"可能已发生、无法确认"），且其处置必须是**人工检查**，不是自动重试或自动回滚。

## 11. 线性化点

涉及并发/竞态的功能，必须用一句话定义**唯一的**线性化点，并显式排除其他候选时点：

> **线性化点**是 <组件内><同步完成><某状态变更并记录结果>的那一步；**不是**用户松键、**不是**发出取消、**不是** HTTP 返回时间。

然后按"谁先到达线性化点"穷举两种顺序的结果，并用**屏障/调度器**验证这两种顺序——不靠随机 sleep 碰运气。

**明确声明不提供的保证**：如果某个更强的语义（如"取消后绝不可能出现文字"）在当前架构下无法保证，写下来：

> 严格要求 X 无法靠普通异步消息保证。如用户要求这一更强语义，**必须另行评审**；本稿不偷偷声称已满足。

这是本规范里最反直觉、也最省事的一条：承认做不到，比事后解释为什么"以为做到了"便宜得多。
