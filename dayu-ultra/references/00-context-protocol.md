# 长上下文作业协议

> **来源声明**：本文件**不是**原项目文档的搬运。原文档里只有散落的支撑事实——最明确的一条是"若新会话继续，请将这两份文档作为上下文；**不能依赖跨会话记忆代替设计约束**"，以及"保留原始证据的日期与验证范围"的纪律。本文件把那些散落纪律**显式化为一份可执行的上下文协议**，并补充了读取分层、会话恢复清单、写回清单与交接格式。凡属新写的机制，均在本文件中直接说明；其余部分与原文档一致。

## 1. 第一原理

**文档是外部记忆，不是交付物。** 在一个跨越多会话的项目里：

- 没写下来的东西 = 下个会话不存在 = **等于没做**
- 写在聊天记录里的东西 = 同样不存在（会话会丢）
- 只有落在项目文档里的东西 = 真实存在

由此推出本协议唯一要保证的性质：**任何一次新会话，只读有限的几个文件，就能恢复推进所需的全部关键状态，且不会把未决事项误当成已决。**

## 2. 单一入口

项目 `docs/` 下必须有一个 `00-index.md`，任何会话的**第一个动作**是读它。它必须在一屏内回答：

| 字段 | 内容 |
| --- | --- |
| 当前阶段 | 阶段 0–6 中的哪一个 |
| 当前节点 | 正在推进的里程碑 `M` 编号 |
| 本会话目标 | 一句可演示的行为（见 §4） |
| 已冻结 | 哪些契约已冻结 + 冻结日期 |
| 待批准 | 哪些决策在等用户拍板（列 `Q` 编号） |
| 阻塞 | 当前 BLOCKED 项 + 解除条件 |
| 下一步 | 下一个动作（具体到文件与命令） |
| 文档版本 | 各文档的版本号/日期，用于识别陈旧副本 |

**索引超过一屏，就已经失效。** 它是指针，不是内容：所有细节留在各自文档里，索引只放"在哪"和"现在什么状态"。

## 3. 三级读取（控制读取预算）

不要一次性读完所有文档。按需分层：

| 层 | 内容 | 何时读 | 预算 |
| --- | --- | --- | --- |
| **T1 常驻** | `00-index.md`、决策登记表的"未决项"部分、当前里程碑卡片 | 每次会话开工 | 必须能全部装下 |
| **T2 阶段** | 当前阶段的 `references/` 分册、当前节点涉及的**已冻结契约** | 进入该阶段时 | 只读与当前节点相关的那几份 |
| **T3 按需** | 完整设计文档、HLD、全部证据日志、历史执行记录 | 被具体问题指向时 | 用检索定位，不要通读 |

**判据**：如果推进当前故事需要 T3 的某个文件，说明 T1/T2 缺少该摘要——把摘要补进 T1/T2，而不是每次会话重复读 T3。

## 4. 会话开工清单

按顺序执行，不要跳：

1. 读 `00-index.md` → 确认阶段、节点、**文档版本**（识别是否读到陈旧副本）。
2. 读决策登记中**影响当前节点**的行 + 全部未决项。**未决项不得当作已批准值使用。**
3. 读当前节点的**已冻结契约**取值表。没有冻结值的地方，就是不能开工的地方（→ 转 DoR 检查）。
4. 读当前故事的 DoR 状态（`references/02-planning.md`）。DoR 未满足 → 先补 DoR，不写业务代码。
5. **声明本会话要推进的那一个可演示行为**，一句话。多个 → 拆开，本会话只做一个。
6. 声明本会话预期产出的证据类型（T/C/H/D，见 `references/03-development.md`）。

第 5 步是本协议的核心约束：**一次会话只推进一个可独立演示的行为增量**。这既是 Agile 的要求，也是上下文预算的要求——"固件全写完再写主机再集成"在任何上下文窗口下都会失败。

## 5. 会话收工清单

**没写回 = 下个会话不知道 = 本次工作不存在。** 收工前逐条检查：

| 产生了什么 | 写回哪里 |
| --- | --- |
| 新的决策 / 批准 | 决策登记表：答复日期、明确选项、**该批准不覆盖什么** |
| 新的未知 / 缺口 | 缺口台账：缺口、需要的证据、当前临时口径 |
| 执行过的测试 | 执行记录：状态枚举（`NOT_RUN`/`BLOCKED`/`FAIL`/`PASS`/`NOT_APPLICABLE_APPROVED`）+ RED/GREEN 证据 |
| 契约变更 | 冻结文档：**更新版本 → 同步契约测试与受影响回归 → 记录 ADR** |
| 文档间的冲突 | 登记冲突 + 修订**所有**受影响文档 + ADR |
| 新的风险 / 残余风险 | 证据记录的"残余风险"字段 |
| 状态变化 | 更新 `00-index.md` 的阶段/节点/阻塞/下一步 |

**只追加，不涂改历史。** 已记录的证据保留其原始日期与验证范围；修正以新增条目表达（"原表述 X 不精确，已修订为 Y，原因 Z"），不要静默改写旧结论——静默改写会让"某结论何时被推翻"这件事永久丢失。

## 6. 跨会话交接块

在 `00-index.md` 末尾维护一个固定格式的交接块，供下一次会话直接消费：

```markdown
## 交接（最后更新：YYYY-MM-DD）

- 阶段/节点：阶段 N / M3
- 本次完成：<可演示的行为> + 通过的用例 ID
- 本次未完成：<明确写出> + 阻塞原因
- 下一步：<具体动作，到文件/命令粒度>
- 待用户决定：<Q 编号 + 问题 + 最迟何时需要>
- 不要重复询问：<已批准的事项清单>
- 已知不可信：<哪些结论是旧的/未实测的/上游的>
```

最后三项尤其重要：**"不要重复询问"**防止每个新会话都从头问一遍已批准的产品选择；**"已知不可信"**防止把历史实验或上游声明当成本项目实测结论。

## 7. 上下文快满时的正确动作

顺序不能反：

1. **先写回**（§5 全部条目）——状态落盘优先于一切。
2. 再做压缩/摘要/开新会话。
3. **绝不为了省 token 而跳过写回。** 省下的 token 会让下一次会话从头再来，总成本更高。

如果发现"要写回的东西太多、写不完"，这是**信号**而不是意外：说明一次会话推进的增量太大，或文档结构需要拆分。按 §8 处理。

## 8. 文档分层与拆分

上下文预算问题的一大半是文档结构问题：

- **一文档一职责**：需求 / 契约 / 测试矩阵 / 证据日志 / 决策登记 各自独立。不要把所有内容堆进一个巨型设计文档——巨型文档无法按需加载。
- **活跃区 vs 冻结区**：仍在变动的写在工作区；已冻结且不再改动的契约转入只读的冻结区，并标注冻结日期。冻结区不再进入日常读取。
- **证据日志按节点分目录**（如 `evidence/M3/`），附 manifest。避免一个不断增长的单一日志文件。
- **单文件超过约 400 行时，考虑按"读者是谁、何时读"拆分**，而不是按主题平均拆。

## 9. 防漂移清单

长上下文项目最常见的四种漂移，各自的检测与处理：

| 漂移 | 症状 | 处理 |
| --- | --- | --- |
| **把未决当已决** | 文档里出现了一个没人批准过的数值 | 立即改回 `TBD`/`待批准`，登记决策项 |
| **把历史当现状** | 引用上个月的实验结果当作当前代码已通过 | 每条证据带日期与验证范围；跨版本引用必须重新验证 |
| **ID 冲突/复用** | 同一个用例 ID 出现在两处、含义不同 | ID 不复用、不跳号；已发布 ID 永久保留其含义 |
| **结论只改一处** | 修正了一个文档，其他引用它的文档还是旧说法 | 修正时搜索全部引用点，同步修订（`references/decisions.md`） |

**每次会话开工时做一次 30 秒漂移自检**：索引里的"当前状态"与各文档的最新条目是否一致？不一致就先修索引。

## 10. 与其他文件的关系

- 证据怎么标注 → `references/evidence.md`
- 决策与契约怎么登记 → `references/decisions.md`
- ID 与追踪链路 → `references/ids.md`
- 索引模板 → `references/templates/00-index.md`
