# 阶段 3：开发

开发阶段的核心不是"写代码"，而是**在写之前决定这段代码需要什么级别的证据**。

## 1. Selective TDD：先分类，再动手

不是所有代码都走"先红后绿"。开场先给这段工作分类：

| 类别 | 适用范围 | 必需证据 |
| --- | --- | --- |
| **T**：必须测试先行 | 真实业务逻辑：状态机、幂等、去重、限额、竞态、时序、解析、清理、访问控制 | 真实的 **RED → 最小 GREEN → 重构回归** 顺序记录 |
| **C**：契约/集成优先 | 外部适配器：第三方 API、平台 API、IPC、序列化、上游类型 | 可先探索；**合入前有可重复的契约测试**，不能只测 mock |
| **H**：实机/人工验收 | 物理与感官：硬件行为、无线协商、按键、电池、显示、音频质量、系统策略 | 真实设备/系统观察 + **环境记录**；单元测试不能替代 |
| **D**：文档/配置/资源 | 人类可读文档、许可证、生成资源、锁文件、构建配置 | 结构/生成/构建/**来源审查** |

规则：

- **T 与 C/H 可叠加**（例如某个逻辑既是业务规则又要跨进程）。层级可写作 `T+C`、`C+H`。
- **高风险行为若因依赖真实硬件而无法先写小测试，应先拆开业务规则与外设边界**，而不是用"胶水代码"逃避 T 类规则。
- **不设虚构的覆盖率百分比。** 覆盖率只能发现空白；关键行为由追踪矩阵、错误注入、真实端到端结果判定。

## 2. RED 的严格定义

**RED 必须因缺失或错误的行为而失败。** 以下都**不算** RED（它们是环境问题，不是行为证据）：

模块无法导入 / 工具未安装 / 凭据缺失 / 网络断开。

正确的 RED 例子：**错误的目标被写入**、**到期后仍可重试**、**缺片仍调用了下游**。

- 允许先搭建必要的测试接口或最小空壳。
- **不能先完成业务实现，再补一条"看起来红过"的记录。**
- **已通过的上游特征测试不要故意破坏来伪装 TDD**——其类别记为 C；新行为再走 T 类循环。

## 3. 每个 T 类故事的证据字段

收工时逐字段填齐，缺字段等于没有证据：

| 字段 | 内容 |
| --- | --- |
| 需求 ID | `R…` |
| 契约 ID | `C…` / `A…` |
| 用例 ID | `TX-…` |
| 待测组件 | 具体到模块/函数 |
| 输入 fixture 版本 | fixture 的来源与哈希 |
| RED | 命令 / 退出码 / **断言**（断言必须体现业务规则） |
| GREEN | 命令 / 结果 |
| 代码版本 | 提交哈希或内容哈希 |
| 相关回归 | 跑了哪些、结果如何 |
| 人工/实机证据 | 路径（H 类必填） |
| **残余风险** | 这次没覆盖到什么 |

最后一项常被省略，但它是下一轮规划最重要的输入。

## 4. Evolutionary Design：什么冻结、什么可演进

先把两者分开写下来：

| 不变（invariants） | 可演进（evolvable） |
| --- | --- |
| 安全边界、数据最小化、不可自动执行的操作 | 实现语言、内部结构、UI 布局、超时默认值、框架选择 |
| 用户已确认的核心行为 | 协议编码细节（在冻结时间点之前） |

规则：

- **可演进的改动必须通过现有行为测试**——这是"可演进"的前提；没有测试的地方谈不上可演进，只算失控。
- **两端第一次独立实现前冻结最小互操作契约**；不提前建设多供应商、集群、OTA、通用插件框架。**无关未来能力不提前抽象。**
- 对上游复用代码：**保留来源**，先做特征/契约测试再改动；**不删除原有实现来制造"测试先行"的历史**。

## 5. Spike（限范围研究）

消除外部未知用 spike，不用"边写边猜"。开工前写下三件事：

1. **假设**：我认为会发生什么
2. **判定方法**：怎么算证实/证伪
3. **终止条件**：什么情况下停止

收工记录结果。两条硬规则：

- **研究代码不得未经生产验收直接进入发布包。**
- spike 出口可以是"**不支持**"，但它**不算功能交付**——返回设计并向用户说明，**不静默降低需求**。

## 6. 测试隔离与替身边界

见 `references/evidence.md` §8。要点复述：

- 可替身：时钟、远端响应、收包调度。
- 必须真实：状态机、解析器、请求生成、去重、清理。
- 用**屏障/调度器**控制顺序，**不靠 sleep 碰运气**。
- **黄金期望不能由待测代码生成。**

## 7. 每轮循环

一次循环只推进**一个可独立演示的行为**：

```
1. 确认该故事的 DoR 已满足
2. 按 T/C/H/D 分类，写用例（阶段 4 的格式）
3. T 类：先写断言 → 观察真实 RED → 最小 GREEN → 重构
   C 类：契约测试先行/同步
   H 类：准备真实设备与记录方式
4. 跑回归
5. 演示（含失败场景）
6. 记录证据（§3 字段）
7. 写回文档（见 references/00-context-protocol.md §5）
8. 确认下一条故事
```

## 8. 缺陷修复的纪律

- **关键缺陷先补能复现的回归测试**，再修。
- **根因修复，不是症状修复**：找出所有同类调用点，在共享接缝处修一次。
- **不删除失败测试，不降低断言来变绿。**
- 修复后按回归用例重测。
- 修复方式本身若改变了契约 → 走契约变更流程（`references/decisions.md` §8）。

## 9. 开发阶段的常见破口

| 破口 | 表现 | 防法 |
| --- | --- | --- |
| 用任意数字开工 | 常量没批准就先写死 | §1 的常量批准前置 |
| 假 RED | 记录里 RED 是"模块导入失败" | §2 的 RED 定义 |
| 只测 mock | 断言"调用了依赖"而不是"产生了行为" | C 类要求可重复契约测试 |
| 顺手加功能 | 实现了被"明确不做"排除的能力 | 每轮对照契约的"明确不做"节 |
| 静默降级 | 门槛达不到就换个口径 | 未达标回决策，见 `05-acceptance.md` |
| 证据不留版本 | 事后无法重现 | §3 的代码版本与 fixture 版本字段 |
