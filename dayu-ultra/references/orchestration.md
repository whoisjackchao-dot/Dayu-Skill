# 编排：委派协议

ultra 的核心动作是**在正确的阶段把正确的工作交给正确的技能，同时保证本规范要求的产物落地**。

## 1. 三条原则

**① 委派的是过程质量，不是交付责任。**
`grill-me` 负责把需求问清楚，`writing-plans` 负责把计划写好，`test-driven-development` 负责循环纪律——但 **`R`/`Q`/`M`/用例/证据这些产物仍由本规范要求并验收**。协作技能做得好，不等于产物齐了。

**② 按需委派，不按图索骥。**
下表是"**可以**委派"，不是"**必须**委派"。判据：**不委派会不会明显降低这一阶段的质量？** 不会就别调——机械全调用只会烧上下文、增加形式负担。

**③ 委派要有边界和回写。**
每次委派都写清：目标、输入产物、期望产物、**不要做什么**、产物回写到哪。没有回写的委派等于白做。

## 3. 委派交接块

委派时给出**有界**的上下文，不要把所有文档倒进去。固定格式：

```markdown
【委派】<技能名>
阶段：<0–6> / 节点 <M<N>>
目标：<一句话，可判定>
输入：<已有产物的**路径**，不要贴正文>
期望产物：<具体制品名>
边界：<明确不要做什么——尤其"不要修改 X 文档">
回写：<产物写到哪个文件的哪一节>
```

**为什么要写"边界"**：协作技能各自有主张（superpowers 的 TDD 会想给所有代码加测试，`grill-me` 会想一直问下去）。不划边界就会越界、就会与 `references/` 的规定打架。

**为什么要写"回写"**：协作技能的产出默认留在对话里，而对话会丢。不回写 = 下个会话不存在 = 等于没做。

## 4. 反模式

| 反模式 | 为什么错 | 正确做法 |
| --- | --- | --- |
| **机械全调用** | 每个阶段都把 4 个栈全上一遍，上下文爆炸、指令互相矛盾 | 按 §2 的信号表按需委派 |
| **把协作技能的输出当证据** | superpowers 说"测试通过"是它自己流程的结论，不是本项目的验收证据 | 证据只认 `docs/07-evidence-log.md` 里带环境/版本/命令的记录 |
| **委派后不落地** | 产物留在对话里，会话一结束就没了 | 强制"回写"字段 |
| **用 superpowers 的 TDD 覆盖 T/C/H/D 分类** | 会把实机/硬件类工作强行套单元测试 | 分类门先行，只对 T 类加载 TDD（见 SKILL.md §3.1） |
| **一次性加载所有协作技能** | 上下文被无关规则占满 | 一次只加载当前阶段需要的 1–2 个 |
| **依赖缺失却假装有** | 伪造证据，本规范最严重的违规 | 显式降级并写进索引的"已知不可信" |
| **两个规范冲突时静默择一** | 后续会话会反复摇摆 | 登记到决策表，写明裁决与理由 |

## 5. 编排与长上下文的关系

编排表是**上下文预算的分配器**：它决定了每次只加载哪 1–2 个协作技能，而不是全部。

- 会话开工：`arming-thought`（若已由宿主自动注入则不重复加载）+ 本规范的 `00-context-protocol.md`
- 当前阶段：本规范该阶段的 `references/` 分册 + §2 表里对应的 1 个协作技能
- 其余一切：按需，不通读

若一次会话里加载了超过 3 个协作技能，**这是信号**：说明本会话的工作包太大，应当拆成多个会话（见 `references/00-context-protocol.md` §9 的防漂移与拆分）。
