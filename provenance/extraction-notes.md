## A. 测试用例规格机制（主要出自 D1）

### A.1 用例书写格式

**A.1.1 表格列结构（原文明示）**

| 项 | 原文依据 |

| G 可省略（只写 W） | D1 BLE-04：「W已冻结帧在MTU23、247下编码与重组」；D1 ASR-01：「W向受控服务提交完整30秒段」（该行无 G 段） |

**A.1.2 用例 ID 命名规则**

原文未集中给出“ID 命名规则”定义段，规则由全表事实呈现：

| 前缀 | 出处章节（D1 标题） | 覆盖范围（原文用例内容） |
| --- | --- | --- |
| TUI | §2 安全填入与会话隔离 | 草稿填入、route/session 校验、rebind、operationID 去重、容量 |
| TX | §3 语音事务、时限与取消 | 按键、硬停、ASR 重试 TTL、取消、休眠/锁屏、BLE 断连 |
| BLE | §4 BLE、安全、codec与完整性 | bond/加密、MTU、分片重组、序号回绕、END、摘要 |
| ASR | §5 ASR请求与数据最小化 | 请求格式、错误分类、出站最小化、真实云调用、准确率评分 |
| ST | §6 状态、用量与提醒 | 状态快照、用量累计、提醒音 |
| SEC | §7 生命周期、隐私、界面与发布 | token、能力面、凭据、隐私哨兵、回调撤销、资源清理 |
| UI | §7 同上 | 首启、截断、息屏、USB 切换、提示音、手势 |

> [推断] 类型代码（T/C/H/D）不进入 ID，只进入“层级”列（如 TUI-17 为 `T+C`，TUI-16 为 `C+H`）。

### A.5 追踪矩阵的结构与维护

**A.5.1 矩阵本体（D1 §9「R01—R24追踪」）**

表头（原文）：`| 需求 | 对应测试ID | 节点 |`

| 列 | 取值示例（原文） |
| --- | --- | --- |
| 需求 | `R01` … `R24` |
| 对应测试ID | `TUI-01, REL-01` / `BLE-01, BLE-02, BLE-03` / `TX-10, TX-11, TX-12, SEC-04, SEC-05` |
| 节点 | `M1,M6` / `M2` / `M3,M4` / `M4,M5` |

一个需求对多个测试、多个节点：24 行中 `R01`→`TUI-01, REL-01`／`M1,M6`；`R20`→`UI-03, UI-04, PERF-03, PERF-04`／`M4,M5`。

**A.5.2 需求 ID → 契约/决策 ID → 测试 ID → 里程碑节点 这条链路的实际表达方式**

- 需求→测试→节点：**由 §9 矩阵三列直接表达**（`需求 | 对应测试ID | 节点`）。
- 契约/决策→用例：**不在矩阵列中**，而以三种方式内联表达：
  1. 用例状态由依赖决定：D1 头部「依赖未批准Q项或未冻结契约的用例为BLOCKED」。
  2. 用例断言正文内联引用：D1 TX-13「远端在途按C03裁决」、D1 TX-17「在途请求按C03裁决」、D1 TUI-13「按C03/C04取得取消/终态证明或保留不确定」、D1 SEC-05「未确认在途请求按C03报告」、D1 ASR-04「完整录音按TTL保留」。
  3. 决策项批准后写入用例注记：D1 头部「Q08取消规则已于2026-09-15批准：TX-10/TX-11/TX-12的取消先后与不确定结果判定已有用户依据」；D1 TUI-18「Q09已批准」；D1 UI-06「G按Q06分工」；D1 §8「Q03门槛…」「Q04门槛已批准但语料待冻结；专项可靠性条件仍待Q05确认」。
- 契约→里程碑的映射在 D2 侧表达：D2 §4「契约冻结状态」表列 `| 契约 | 状态 | 说明 |`，行含「M1 桥接契约 ✅冻结」「M2 BLE 线协议 ⏳清单就绪…M2 前冻结」「M3 ASR 验收 ⏳清单就绪」「M4 字体/按键/电源 ⏳未开始」。
- 批准值→契约→验收基线：D2 §7 末「上述取值已写入 [M1 桥接契约冻结](./contracts/M1-桥接契约冻结.md) 第 5/7 节，作为验收基线。」
- 需求条目→契约：D2 §1「M1 契约冻结 ✅ 已冻结（BR-01—06 路径/认证/状态码/容量/期限）」。

> [推断] 完整的四段链路（需求→契约/决策→测试→节点）**不是单表表达，而是跨 D1/D2 两份文件拼合**：D1 §9 给“需求→测试→节点”，D1 头部/用例注给“决策/契约→测试状态”，D2 §4 给“契约→里程碑”。D1/D2 均未出现四列合一的矩阵。
> [推断] D1 §6 注「其他依赖仍须按DoR核查」中的 DoR 即 D2 这份“开发准备就绪核查”所执行的检查。
