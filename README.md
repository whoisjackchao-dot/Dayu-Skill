# dayu

一套**项目全生命周期规范**，用于把"需求分析 → 规划 → 开发 → 测试 → 验收 → 交付"跑成有据可查、可跨会话接续的过程。

- **给 agent 看**：`SKILL.md`（路由 + 铁律 + 阶段模型）。这是技能的入口，DSH 与 OpenCode 都读它。
- **给人看**：本文件。说明它是什么、从哪来、为什么叫这个名字。

---

## 名字由来

**dayu（大禹）**——治水十三年。

| 大禹的事迹 | 对应的机制 |
| --- | --- |
| 父鲧用堵、失败；禹改用**疏导** | 可逆决策不提前冻结；演进式设计靠现有行为测试兜底，而不是一次冻死 |
| **划天下为九州** | 里程碑纵向切分：每一块都能独立演示，而不是"模块全写完再集成" |
| **铸九鼎** | 契约冻结：把关键取值固化成不可随便动的基线 |
| **三过家门而不入** | 节点按证据关闭，**不按时间自动完成** |
| **《禹贡》** | 分级、分区、可复核的系统化记录 |
| 十三年长周期 | 长上下文：靠制度与文档维系，而不是靠记忆 |

一个形象同时覆盖了规划切分、契约固化、演进式设计、按证据关闭节点——正好是这套规范的六阶段主干。

| **仓颉** | 造字、结绳→书契——最贴"文档即外部记忆、契约固化、落地不可抵赖" | 偏"记录"，对推进节奏与验收纪律表达较弱 |

### 命名约束

技能名必须是 ASCII 小写 kebab-case（OpenCode 要求 `^[a-z0-9]+(-[a-z0-9]+)*$`），且**必须与目录名一致**，因此用拼音 `dayu`，并**不加限定词**——路由职责由 `description` 承担，名字只负责气质。

## 来源

本规范不是凭空设计的，而是从一套在真实项目上跑过的流程产物中抽出来的。原始材料包含十份中文文档：主设计文档、功能模块 HLD、方法论审查与决策登记、契约与演进设计补充、测试用例与追踪矩阵、交付节点与完成定义、可行性核查、开发准备就绪核查，以及四份契约冻结文件。

提取方式：三份方法论最密的文档逐字通读；其余六份派子代理并行提取，要求**逐条附原文出处**、**领域专属与通用分开**、**推断显式标注 `[推断]`**。原始提取结果保留在 `provenance/extraction-notes.md`。

抽取原则：**留机制，去领域**。具体芯片、协议、云服务、编辑器 API 全部剔除，只保留可迁移的机制——证据分级、决策登记、契约冻结、追踪矩阵、DoR/DoD、里程碑卡片。

### 唯一的新增部分

`references/00-context-protocol.md`（长上下文作业协议）**不是原文搬运**，是为了满足"长上下文场景"这个目标新写的。原文只有散落的支撑事实，最硬的一条是：

> 若新会话继续，请将这两份文档作为上下文；**不能依赖跨会话记忆代替设计约束。**

该文件顶部有明确的来源声明。其余部分均可追到原文。

### 一处已纠正的误归因

初稿曾在长上下文协议里写"ID 不复用、不跳号"并当作既有规则。子代理核查后指出**原文没有这条依据**。现已改为显式标注："此处作为工程纪律由本规范补入，非原文搬运。"

## 安装位置

同一份 `SKILL.md` 同时被两个系统识别——它们实现的是同一套 Agent Skills 约定，只是查找路径不同：

| 系统 | 路径 |
| --- | --- |
| DSH | `~/.dsh/skills/dayu/` |
| OpenCode | `~/.config/opencode/skills/dayu/` |

约束（两个系统都适用）：`name` 必须匹配目录名、`description` 不超过 1024 字符、frontmatter 只含被识别的字段（`name` / `description` / `license` / `compatibility` / `metadata`）。

修改本目录后需同步到上述两处并重新校验 frontmatter。

### OpenCode 启动器：`/dayu`

技能平时靠 `description` 自动路由（任务描述命中触发词即加载）。若想要一个**确定性入口**，可加一个斜杠命令，放在 `~/.config/opencode/command/dayu.md`：

```markdown
---
description: 加载 dayu skill 并按全生命周期规范推进项目
---

先调用 skill 工具加载 skill `dayu`，然后严格按它的要求工作：

- 若项目还没有 `docs/` 骨架，先按 `references/templates/README.md` 的填写顺序建骨架
- 开工先读 `docs/00-index.md`，声明当前阶段与本会话要推进的**那一个**可演示行为
- 未批准的取值一律登记为待决，**不得当事实使用**
- 收工前把决策、缺口、证据、状态写回文档

用户的任务 / 问题：

$ARGUMENTS
```

用法：`/dayu 帮我给这个新项目立项`

> 命令是**配置期文件**，新建或修改后必须**重启 OpenCode** 才生效——OpenCode 不做热重载。
> 同理，技能文件本身改动后也要重启。TUI 内置命令里没有 reload 一类的东西。

---

## 什么时候不要用

- 单文件、单次会话能完成的小改动——本规范的产物成本高于收益。
- 纯粹的信息查询。

判断标准：**这个项目会不会跨越多次会话、需要向他人证明结论的真实性？** 两个都否，就不必动用全套。
